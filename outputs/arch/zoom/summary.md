# Exp 2 + Exp 8：原生块内 zoom 与缩减共享前缀（免训练）

**结论。** ScreenSpot-Pro 原生分辨率，1,581 题：

- 把裁剪图放进每个问题自己的块里，并让块内所有 token 在全注意力层里看不到整图 token（layout `alliso`；整图仍然通过 GDN 状态进入），准确率从第一遍的 50.1 升到 **61.8**。共享前缀完全不动。
- 这个结果比旧的 zoom 做法（对裁剪图另起一次 prefill，60.7）高 1.1。
- 再叠加 GUI 路径 α = 0.5（实验 1），得到 **68.75** [66.4, 71.0]。这是零训练结果，高于之前 zoom 赛道最好的 62.2，也高于 KV-Ground-4B 的 67.0，和 UI-Venus-1.5-8B 的 68.4 打平（这两个数字来自 sprint 报告的文献值）。底座生成式是 59.9。

训练 zoom 这一步（Z1：LoRA + 头；Z2：只训头）都没有超过零训练配方，见 `outputs/arch/phase2/DECISION_zoom.md`。

## 准确率（`results.json`，95% CI 为 bootstrap；Δ 是相对同一次运行第一遍的配对差）

| 设置 | 前缀 token（中位） | 第一遍 | zoom 后 | 另起 prefill 基线 |
|---|---|---|---|---|
| 原生，`pre`：裁剪 token 看得到整图 | 4080 | 50.1 | 57.4（+7.3 [+5.5, +9.2]） | 60.7 |
| 原生，`alliso` | 4080 | 50.1 | **61.8**（+11.7） | 60.7 |
| 原生，`alliso`，α = 0.5 | 4080 | 57.8 | **68.75** | 68.4 |
| 原生，`alliso`，α = 0.5，3 个候选裁剪按门控选 | 4080 | 57.8 | 69.1（任一候选命中的上限 76.5） | — |
| 4096 上限，`pre` | 3950 | 46.8 | 56.9 | — |
| 2048 上限（粗前缀），`pre` / `alliso` | 2040 | 36.2 | 51.5 / 55.5 | — |
| 原生，裁剪上限 576 token，`pre` | 4080 | 50.1 | 53.5 | — |
| 在 1/5 子集上比较三种 layout | | 52.1 | `pre` 60.9；`pre_iso` 57.7；`alliso` **65.6**；`post` 11.3 | 62.1 |

几点解释：
- 只把裁剪 token 和整图隔开（`pre_iso`）反而更差。要连问题 token 也看不到整图 token（`alliso`）才最好。
- 把裁剪放在问题之后（`post`，裁剪 token 能看到问题）会彻底失败：头没有见过以问题为条件的视觉 token。
- 门控挑选多候选几乎不涨分：门控分辨不出哪张裁剪对，但 oracle 上限 76.5 说明候选本身已经覆盖了目标。挑选可以作为后续训练的方向。

## 实验 8 的判定：问题无关的前缀缩减不值得单独做
- 保留原始 2D 位置、只留像素方差最大的 50% token：LLM prefill 从 262 ms 降到 149 ms，但 ViT 一点没省（315 ms），整体只快 18%，准确率却掉 5.6 点（50.1 → 44.4）。
- 同样是约 2,040 个 token，保留位置的剪枝（44.4）明显好于整体降分辨率（36.2）。这说明 GAP 文献里"保留位置 ID"的结论在这里成立，只是速度收益太小。
- 更好的折中是"粗共享前缀 + 每题细看"。4096 上限加 zoom、α = 0.5：一个问题 491 ms，准确率 69.2，比原生单遍（613 ms，50.5）更快，也高 18.7 点。同一张截图上每多问一个问题只多 122 ms。
- 和 vLLM 比：sprint 测的是 4096 token 截图、单问题，vLLM 开前缀缓存、FP8 + MTP 时 262 ms，底座 4000 token 的准确率 56.0。我们这里是没有优化的 eager 引擎，绝对毫秒数不能直接对比。可以对比的是"准确率随问题数扩展"的结构。按问题数计的吞吐，需要用 `speed/engine.py`（已拆到 glance-engine）重新实现块内 zoom 后再测，这属于工程工作，按协调者的安排暂缓。
